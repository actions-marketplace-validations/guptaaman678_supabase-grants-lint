# GL001 missing-service-role-grant

Default severity: **error**.

## What it catches

A table, view, materialized view or foreign table created in an enforced migration where, at the
end of that migration, `service_role` holds no table privilege at all. Relations dropped again in
the same migration are not reported. A grant in a later migration does not count: the relation is
unreachable from the moment the first migration is applied.

## Why it matters

`service_role` bypasses row level security, but it does not bypass grants. Postgres checks table
privileges before it looks at any policy. Without automatic grants, server-side code that uses the
service role key (edge functions, cron jobs, admin tools, backend services) gets
`42501 permission denied for table` on the new table, even though it has "full access" everywhere
else.

## Failing example

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_todos.sql
create table public.todos (
  id bigint generated always as identity primary key,
  user_id uuid not null default auth.uid(),
  title text not null
);
alter table public.todos enable row level security;
grant select, insert, update, delete on public.todos to authenticated;
create policy "Users manage their todos" on public.todos
  for all to authenticated using (auth.uid() = user_id);
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20261002120000_add_todos.sql
  2:1  error  GL001  public.todos is created without a grant to service_role: server-side requests as service_role (edge functions, admin tools) fail with 42501 permission denied, because service_role bypasses RLS but not grants. Grant it the privileges it needs in the same migration.
              fix   grant select, insert, update, delete on public.todos to service_role;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL001.md

1 error, 0 warnings  (2 files, 1 relation, 0.0s)
```

## Fix

Grant `service_role` the privileges your server code needs, in the same migration. Views and
materialized views are read through, so they need `select` only.

```sql
-- supabase/migrations/20261002120000_add_todos.sql
create table public.todos (
  id bigint generated always as identity primary key,
  user_id uuid not null default auth.uid(),
  title text not null
);
alter table public.todos enable row level security;
grant select, insert, update, delete on public.todos to authenticated;
grant select, insert, update, delete on public.todos to service_role;
create policy "Users manage their todos" on public.todos
  for all to authenticated using (auth.uid() = user_id);
```

If the migration is already applied, put the grant in a new migration instead and add an `ignore`
entry for the old file, with the reason.

## When it is safe to disable

When no server code ever touches the relation as `service_role`, for example a table only
database functions running as their owner read. Prefer an `ignore` entry for that relation over
turning the rule off.

## Configuration

- [`serviceRole`](../configuration.md#servicerole) names the role (default `service_role`).
- [`serviceOnly`](../configuration.md#serviceonly) does not exempt a relation from GL001.
- Suppress one finding with `-- grants-lint-disable-next-line GL001: <reason>` on the line above
  the `create` statement, or an [`ignore`](../configuration.md#ignore) entry.
