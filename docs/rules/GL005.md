# GL005 blanket-grant

Default severity: **warn**.

## What it catches

A `grant ... on all tables in schema <schema>` or `grant ... on all sequences in schema <schema>`
in an enforced migration, on a checked schema, to a client role (`anon`, `authenticated`, a role in
[`clientRoles`](../configuration.md#clientroles), or `PUBLIC`) or to `service_role`. One finding
per statement. Revokes are not reported.

## Why it matters

A blanket grant applies to every table or sequence that exists at that moment, and to none created
later. It re-opens tables an earlier migration deliberately narrowed (an audit log only the server
writes, a table with column-level grants), and it gives the next new table nothing, so it does not
replace per-table grants either. It is often copied from old guides written for projects with
automatic grants.

## Failing example

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_audit_log.sql
create table public.audit_log (
  id bigint generated always as identity primary key,
  event text not null
);
grant select, insert on public.audit_log to service_role;
```

```sql
-- supabase/migrations/20261003120000_add_todos.sql
create table public.todos (
  id bigint generated always as identity primary key,
  title text not null
);
grant select, insert, update, delete on public.todos to service_role;
grant select on all tables in schema public to authenticated;
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20261003120000_add_todos.sql
  7:1  warn   GL005  This grant on all tables in schema public to authenticated applies to every relation that exists there at this point (2 relations), including any deliberately narrowed earlier, and to none created later. Grant on the relations by name instead.
              fix   grant select on public.todos to authenticated;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL005.md

0 errors, 1 warning  (3 files, 2 relations, 0.0s)
```

`public.audit_log` is now readable by every signed-in user. When the migration creates relations,
the fix line grants on those by name.

## Fix

Name the relations the grant is meant for.

```sql
-- supabase/migrations/20261003120000_add_todos.sql
create table public.todos (
  id bigint generated always as identity primary key,
  title text not null
);
grant select, insert, update, delete on public.todos to service_role;
grant select on public.todos to authenticated;
```

## When it is safe to disable

When a schema holds only relations that every listed role should reach in full, and you re-check
that each time a table is added. Even then, a grant by name documents intent better.

## Configuration

- [`schemas`](../configuration.md#schemas) decides which schemas are checked.
- [`clientRoles`](../configuration.md#clientroles) and
  [`serviceRole`](../configuration.md#servicerole) decide which grantees are reported.
- Suppress one finding with `-- grants-lint-disable-next-line GL005: <reason>` on the line above
  the `grant` statement, or an [`ignore`](../configuration.md#ignore) entry.
