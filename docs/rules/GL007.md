# GL007 replay-reenables-defaults

Default severity: **warn** (**error** when `since` was auto-detected and the grant comes after the
opt-in migration).

## What it catches

After replaying every migration, the migrations themselves leave default privileges that give
`anon`, `authenticated`, a role in [`clientRoles`](../configuration.md#clientroles), `PUBLIC` or
`service_role` privileges on new tables or sequences that
[`migrationRole`](../configuration.md#migrationrole) creates in a checked schema.

Only the privileges the opt-in SQL Supabase published removes count: `select`, `insert`, `update`,
`delete` on tables and `usage`, `select` on sequences. A project that opts in with exactly that SQL
keeps `truncate`, `references`, `trigger` (and `maintain`) on tables and `update` on sequences,
both in production and in a replay, so GL007 does not report them;
[GL008](GL008.md) reports them on each new relation instead. Revoking `all`, as in the fix below,
clears both.

Only statements in the files count, not [`platformDefaults`](../configuration.md#platformdefaults)
or the platform revoke assumed at `since`: a replay runs the files alone. GL007 reads every file,
enforced or not, and reports once, at the last `alter default privileges ... grant` that still has
an effect.

## Why it matters

This is the replay trap. A baseline made with `supabase db pull` usually contains
`ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON TABLES TO "anon"`
(and the same for `authenticated`, `service_role` and sequences). Production stops giving new
tables automatic grants, but every environment built by replaying the migrations turns them back
on: `supabase db reset` locally, preview branches, CI databases. A table without grants then works
in every test and fails with `42501` in production.

## Failing example

```sql
-- supabase/migrations/20240101000000_remote_schema.sql
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON TABLES TO "anon";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON TABLES TO "authenticated";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON TABLES TO "service_role";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON SEQUENCES TO "anon";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON SEQUENCES TO "authenticated";
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON SEQUENCES TO "service_role";
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20240101000000_remote_schema.sql
  1:1  warn   GL000  No opt-in migration found, so the rules that check new relations (GL001 to GL006, GL008) checked no file. If your project was opted in from the dashboard, or you are past 2026-10-30, set since to the last migration applied before that (supabase-grants-lint init --since next). Otherwise add the opt-in migration that supabase-grants-lint doctor prints.
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL000.md
  7:1  warn   GL007  Replaying these migrations (supabase db reset, a preview branch) leaves default privileges that give anon, authenticated, service_role select, insert, update, delete on new tables and usage, select on new sequences postgres creates in schema public, so new relations get grants there that production, with automatic grants off, does not give them. Revoke them in a new migration.
              fix   alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated, service_role;
                    alter default privileges for role postgres in schema public revoke all on sequences from anon, authenticated, service_role;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL007.md

0 errors, 2 warnings  (1 file, 0 relations, 0.0s)
```

GL000 is reported too: this history has no opt-in migration yet.

## Fix

Add a migration that revokes the default privileges (the fix line in the output is the SQL). This
is also the opt-in migration, so it gives the other rules their enforcement boundary.

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

Do not edit the baseline itself: it has already been applied to production.

For local resets, also set `auto_expose_new_tables = false` under `[api]` in
`supabase/config.toml`; `supabase-grants-lint doctor` reports that setting.

## When it is safe to disable

When every environment you replay into should behave like a project with automatic grants, for
example if you never opt in before 2026-10-30 and never use preview branches. After 2026-10-30 it
is not safe.

## Configuration

- [`migrationRole`](../configuration.md#migrationrole), [`schemas`](../configuration.md#schemas),
  [`clientRoles`](../configuration.md#clientroles) and
  [`serviceRole`](../configuration.md#servicerole) decide what is reported.
- Suppress it with `-- grants-lint-disable-next-line GL007: <reason>` on the line above the
  reported statement, or an [`ignore`](../configuration.md#ignore) entry.
