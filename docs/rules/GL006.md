# GL006 default-privileges-regrant

Default severity: **error**.

## What it catches

An `alter default privileges ... grant ... on tables` or `... on sequences` in an enforced
migration that gives privileges to `anon`, `authenticated`, a role in
[`clientRoles`](../configuration.md#clientroles), `PUBLIC` or `service_role`, for the role that
creates your relations ([`migrationRole`](../configuration.md#migrationrole), or the role a
`set role` in the file switched to), in a checked schema or in every schema (no `in schema`).
One finding per statement. Revokes and default privileges on functions are not reported.

## Why it matters

It turns automatic grants back on for every table or sequence created afterwards, which is exactly
what the opt-in removed. New tables then look fine locally and in CI while other environments
(created without that statement's history, or opted in by the platform) behave differently.
Grants stop being visible in the migration that creates each table, so review cannot catch a table
that should not be exposed.

## Failing example

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_orders.sql
alter default privileges in schema public
  grant all on tables to anon, authenticated, service_role;
create table public.orders (
  id bigint generated always as identity primary key,
  total_cents integer not null
);
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20261002120000_add_orders.sql
  2:1  error  GL006  This default privilege gives anon, authenticated, service_role all privileges on every table postgres creates in schema public from here on, turning automatic Data API grants back on after the opt-in. Remove it and grant on each new table by name.
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL006.md
  2:1  error  GL007  Replaying these migrations (supabase db reset, a preview branch) leaves default privileges that give anon, authenticated, service_role select, insert, update, delete on new tables postgres creates in schema public, so new relations get grants there that production, with automatic grants off, does not give them. Revoke them in a new migration.
              fix   alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated, service_role;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL007.md
  4:1  warn   GL008  public.orders still grants truncate, references, trigger to anon, authenticated, left over from the default privileges or a grant all: the Data API never needs them, and TRUNCATE and REFERENCES are not subject to row level security. Revoke them in the same migration.
              fix   revoke truncate, references, trigger on public.orders from anon, authenticated;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL008.md

2 errors, 1 warning  (2 files, 1 relation, 0.0s)
```

GL007 reports the same statement as an error here, because the migrations now re-enable automatic
grants after the opt-in, and GL008 reports the extra privileges the default gave `public.orders`.

## Fix

Remove the statement and grant on each new relation by name.

```sql
-- supabase/migrations/20261002120000_add_orders.sql
create table public.orders (
  id bigint generated always as identity primary key,
  total_cents integer not null
);
grant select, insert, update, delete on public.orders to service_role;
```

If the statement is in a migration that is already applied, add a new migration that revokes the
same default privileges, and suppress the old finding with a reason.

## When it is safe to disable

When the default grant goes to a role you created for a narrow purpose and list in `clientRoles`
only for policy checks. For the Supabase API roles, it is not safe.

## Configuration

- [`migrationRole`](../configuration.md#migrationrole) names the creator role.
- [`schemas`](../configuration.md#schemas), [`clientRoles`](../configuration.md#clientroles) and
  [`serviceRole`](../configuration.md#servicerole) decide what is reported.
- Suppress one finding with `-- grants-lint-disable-next-line GL006: <reason>` on the line above
  the statement, or an [`ignore`](../configuration.md#ignore) entry.
