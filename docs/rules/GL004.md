# GL004 serial-sequence-usage

Default severity: **error**.

## What it catches

A table created in an enforced migration with a `serial` column (`smallserial`, `serial`,
`bigserial`, `serial2`, `serial4`, `serial8`) where, at the end of that migration, a client role
(`anon`, `authenticated`, or a role in [`clientRoles`](../configuration.md#clientroles)) can
`insert` into the table but neither it nor `PUBLIC` holds `usage` or `update` on the column's
sequence (`<table>_<column>_seq`). A grant on the sequence by name, or on `all sequences in schema`
after the table exists, counts.

`nextval()` accepts either privilege. Supabase's announced revoke removes `usage` and `select` on
new sequences but leaves `update`, so in a project opted in from the dashboard (or by the
2026-10-30 change) new serial sequences still give the API roles `update`, and inserts work. The
rule does not report those tables.

Identity columns (`generated always as identity`) and `uuid` keys create no sequence to grant, so
they never trigger this rule.

## Why it matters

A serial column's default is `nextval('<table>_<column>_seq')`, and calling it needs a privilege
on the sequence. Without automatic grants, the table grant alone is not enough: every insert that
relies on the default fails with `42501 permission denied for sequence`, while selects work, so it
often slips through testing.

## Failing example

```sql
-- supabase/migrations/20261001000000_revoke_automatic_grants.sql
alter default privileges for role postgres in schema public
  revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public
  revoke all on sequences from anon, authenticated, service_role;
```

```sql
-- supabase/migrations/20261002120000_add_orders.sql
create table public.orders (
  id bigserial primary key,
  user_id uuid not null default auth.uid(),
  total_cents integer not null
);
alter table public.orders enable row level security;
grant select, insert, update, delete on public.orders to service_role;
grant usage on sequence public.orders_id_seq to service_role;
grant select, insert on public.orders to authenticated;
create policy "Users read their orders" on public.orders
  for select to authenticated using (auth.uid() = user_id);
create policy "Users place orders" on public.orders
  for insert to authenticated with check (auth.uid() = user_id);
```

Output of `supabase-grants-lint check`:

```text
supabase/migrations/20261002120000_add_orders.sql
  2:1  error  GL004  public.orders has serial column id, and authenticated can insert into it but holds no usage (or update) on its sequence public.orders_id_seq: inserts that rely on the column default fail with 42501 permission denied for sequence orders_id_seq. Grant authenticated usage on the sequence in the same migration.
              fix   grant usage on sequence public.orders_id_seq to authenticated;
              docs  https://github.com/guptaaman678/supabase-grants-lint/blob/v0.1.0/docs/rules/GL004.md

1 error, 0 warnings  (2 files, 1 relation, 0.0s)
```

## Fix

Grant `usage` on the sequence to each role that inserts, in the same migration. `update` also
works, but it lets the role call `setval()` too, so `usage` is the narrower grant. For a new table,
an identity column (`id bigint generated always as identity primary key`) avoids the sequence
grant altogether.

```sql
-- supabase/migrations/20261002120000_add_orders.sql
create table public.orders (
  id bigserial primary key,
  user_id uuid not null default auth.uid(),
  total_cents integer not null
);
alter table public.orders enable row level security;
grant select, insert, update, delete on public.orders to service_role;
grant usage on sequence public.orders_id_seq to service_role;
grant select, insert on public.orders to authenticated;
grant usage on sequence public.orders_id_seq to authenticated;
create policy "Users read their orders" on public.orders
  for select to authenticated using (auth.uid() = user_id);
create policy "Users place orders" on public.orders
  for insert to authenticated with check (auth.uid() = user_id);
```

## When it is safe to disable

When clients always supply the column's value themselves and never rely on the default. That is
rare for a serial key; suppress the one table with a reason rather than turning the rule off.

## Configuration

- [`clientRoles`](../configuration.md#clientroles) adds roles to check.
- Suppress one finding with `-- grants-lint-disable-next-line GL004: <reason>` on the line above
  the `create table` statement, or an [`ignore`](../configuration.md#ignore) entry.
